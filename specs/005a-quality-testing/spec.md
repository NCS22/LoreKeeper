# Spec 005a — Quality testing strategy

Status: approved

## Context and goal

The test suite has grown to roughly three quarters of the code written so far (spec 004 alone produced about 3.4 times more test code than production code and took about six hours). Three problems follow: many tests check shallow implementation details instead of behavior, attention goes to the coverage percentage instead of the real quality of the tests, and there is no shared criterion that says which components deserve exhaustive tests and which do not.

Guiding principle: the goal is not more tests; every test must give a real guarantee about the behavior of the application. Testing must accompany development without slowing it down.

This spec is the first of two that share one context (the user's source document of 2026-11-20, `CALIDAD.md`, kept until both are done):

- **005a (this spec)** defines the strategy and produces the knowledge the cleanup needs: criticality classification, coverage policy, criticality inventory, an audit report with a verdict per group of existing tests, a reusable skill for agents, and a test-first (TDD) way of working inside the SDD flow. It changes no existing test, writes no new test of production code and changes no production behavior.
- **005b (written later)** executes the cleanup that the user approves from the audit report, and turns on the automatic coverage thresholds defined here.

The universe lifecycle spec, which was provisionally numbered 005, is renumbered 006.

The spec has 20 functional requirements, above the usual budget of about 12. The user accepted this on 2026-11-20 and keeps them in one spec because they all concern the same subject and each one is small.

Some requirements describe behavior that happens in 005b or later (the re-check of the audit report in FR-9, the proposals of FR-15). In 005a they are satisfied by the rule being written in the skill and in the flow rules; their execution belongs to 005b (FR-9) or starts after 005b closes (FR-15).

### Decisions of the user on 2026-11-20

- D-1. A change that alters behavior in a CORE or IMPORTANT component is written test-first (red, then green). A change that keeps behavior (refactor, rename, move, removal of code without behavior change) adds no new test: the tests that already protect the behavior must pass before and after ("green before and after"). The task list records which of the two happened, with the tests involved (FR-13). Refinement from the QA of 2026-11-20: the single exception is a behavior-keeping change on a CORE or IMPORTANT component whose behavior is not yet protected (a known gap), where characterization tests that pin the current behavior are written first (FR-13).
- D-2. TIER 0 gets no tests, bug fixes included. The rule "every bug fix starts with a reproducing test" applies to CORE and IMPORTANT only (FR-14).
- D-3. After 005b, the skill may propose deleting or simplifying a test, with a written justification that no protection is lost; nothing is deleted without the user's explicit approval at a flow gate, and protected tests are never proposed for deletion, except in the single case of D-6 (FR-15).
- D-4. Constitution amendment, approved by the user on 2026-11-20: the NEVER rule of the project instructions about silencing errors, skipping tests, deleting tests and relaxing strict mode gains the exception "except a justified proposal approved by the user" for deleting or simplifying tests only; silencing errors, skipping tests and relaxing strict mode stay forbidden without exception. The other instructions in the closed list of FR-16 are aligned with "tests proportional to criticality".
- D-5. The user approves, subject to the plan, the component-testing tools (a DOM simulation environment and a component-testing library) so that IMPORTANT interface components are tested at unit level and count toward their target (FR-7). In 005a the tools are only installed and configured.
- D-6. The only case where a protected test may be proposed for deletion is when the production behavior it protects is removed entirely. The proposal goes test by test, needs the explicit approval of the user at a flow gate, and must show that no other remaining path loses its protection (FR-10, FR-13, FR-15). Decided by the user on 2026-11-20.

## Users

- The project owner, who decides what the strategy is and approves every destructive step.
- The AI agents (planner, implementer, reviewer, hacker, coordinator), who must take consistent testing decisions without relying on memory of earlier conversations.

## User stories

- US-1. As the project owner, I want every production component classified by risk so that testing effort goes where a failure would hurt most.
- US-2. As the project owner, I want an audit of the current suite, with a verdict per group of tests, so that I can decide what to keep, rewrite or remove without losing protection.
- US-3. As an AI agent, I want one operational reference and a maintained inventory so that I can answer how much and what kind of testing a change needs without guessing.
- US-4. As the project owner, I want development to be test-first for the components that matter so that tests describe behavior before the code exists and are not an afterthought that inflates the suite.
- US-5. As the project owner, I want the coverage targets measured and their enforcement defined so that the percentage is a quality signal and not a quota.

## Definitions

- **CORE**: a component whose incorrect behavior can compromise the integrity, security or essential operation of the application (authentication and authorization, ownership isolation, spoiler filtering when it exists, critical persistence operations, complex business rules, anything whose failure has serious consequences).
- **IMPORTANT**: a component whose failure significantly harms the user experience or blocks usual tasks (relevant interface components, forms and validations, user interactions, navigation, state handling, user flows, loading, error and empty states).
- **TIER 0**: an element with no relevant behavior, or whose correctness is already guaranteed by static tools (type declarations, constants, declarative configuration, static utilities without significant logic).
- **Relevant logic**: branching, computation, transformation, validation, or any decision whose wrong result a user or the data would notice.
- **Production component**: any element shipped or run by the application: application code, application configuration, the package manifest, the database schema and migrations, design tokens and the message dictionary. Configuration, manifest, schema, tokens and messages are usually TIER 0 unless they contain relevant logic; the integrity of the schema and the migrations is protected by the integration tests of the components that use them. The only production change of this spec is to the development dependencies of the package manifest (and its lockfile) when the tools of FR-7 are approved; that entry is classified TIER 0 (declarative configuration, no tests).
- **Project instructions**: the project instructions file and the rule files (the `.claude` rules), that is, the constitution.
- **Not production**: tests, test support (fakes, contracts, helpers), generated code, test-runner and browser-test configuration, the agent setup (agents, rules, commands, skills) and documentation. Custom lint rules are tooling. None of these is classified.
- **Tooling**: test support and custom lint rules (with their tests). Tooling is not classified; see FR-14 for when a change to it carries tests.
- **Component**: the unit of classification: one production file, or a cohesive set of files with one responsibility and the same risk.
- **Inventory entry**: one row of the criticality inventory. It may group several components only if they share level and test strategy. Every production file belongs to exactly one entry.
- **Test group**: one test file, or a set of test files that protect the same component. Every test file belongs to exactly one group. Test support and tests of lint rules are audited as test groups.
- **Verdict**: one of KEEP (gives real protection), REFACTOR (valid intention, deficient implementation), DELETE (redundant, artificial or without value), REPLACE (a better strategy exists to protect the behavior), REVIEW (information is missing to decide).
- **Protected tests**: the tests that prove that one user cannot read or change another user's data (owner isolation) and, when they exist, the tests that prove spoiler filtering. Protection applies per test, not per file.
- **Red step**: a test written before the code that makes it pass, run and seen failing for the expected reason.
- **Green before and after**: for a change that keeps behavior, the existing tests that protect that behavior pass before the change and again after it.

## Functional requirements

- FR-1: THE SYSTEM SHALL assign every production component exactly one criticality level (CORE, IMPORTANT or TIER 0) based on its risk and behavior, not on its location, size or technology, and SHALL record the reason for the level.
- FR-2: IF a component classified as TIER 0 turns out to contain relevant logic, detected by whoever adds or modifies it or by the reviewer at validation, THEN THE SYSTEM SHALL require it to be reclassified before any decision about its tests.
- FR-3: THE SYSTEM SHALL keep a criticality inventory with one entry per component or per group of components that share level and test strategy, showing for each its main responsibility, criticality level, justification, recommended testing strategy and protection status (measured coverage when available, or "protected by browser test X" when only a browser test protects it), and SHALL record in the entry any coverage exception with its reason and any coverage gap with the plan to close it.
- FR-4: WHEN a task adds, modifies, renames, moves, merges or deletes a production component, THE SYSTEM SHALL have its inventory entry present and up to date by the time the task is done, and SHALL show in the test design section the level that decided the tests; WHEN the project instructions (the project instructions file and the rule files, that is, the constitution), the skill and the inventory disagree, THE SYSTEM SHALL treat the project instructions as the authority over the skill, and the skill over the inventory, and SHALL fix the disagreement in the same task. In this spec FR-4 applies only by adding and keeping the TIER 0 inventory entry of the development dependencies in the package manifest and its lockfile.
- FR-5: THE SYSTEM SHALL define the coverage targets per inventory entry, as quality goals and not quotas (CORE 100 %, IMPORTANT 80 %, TIER 0 none), for lines and branches, and SHALL require a justified exception recorded in the entry when a target cannot be reached without redundant, fragile or low-value tests. A component reclassified upward that is below its new target gets the gap recorded in its entry with a plan to close it, and does not fail any check until the thresholds are turned on in 005b. A test that exercises several components counts toward each component it exercises.
- FR-6: THE SYSTEM SHALL define the quality of assertions as a review criterion, not as a percentage: a test that would still pass if the result were wrong is weak. The criteria SHALL be written in the skill and applied by the audit and by the reviewer.
- FR-7: THE SYSTEM SHALL provide a way to measure line and branch coverage of the production components from unit and integration tests, reported per inventory entry and stating which test types contributed to it; behaviors protected only by browser tests are recorded in the inventory, not measured. This FR depends on the approval of new development dependencies, asked for in the plan of this spec: the coverage provider and, per D-5, a DOM simulation environment and a component-testing library. IF the coverage provider is refused, THEN the plan SHALL propose an alternative that measures coverage without adding it. IF the component-testing tools are refused, THEN the plan SHALL extract the logic of interface components into pure functions tested at unit level and protect the visual behavior with a few browser tests. WHEN the tools are approved, THE SYSTEM SHALL only install and configure them in this spec, without changing the outcome of any existing test, and SHALL write no component test here; IMPORTANT interface components get unit tests when they are next touched (FR-13) or in spec 005b, and from then count toward the 80 % target.
- FR-8: THE SYSTEM SHALL define the policy for automatic coverage thresholds (CORE 100 %, IMPORTANT 80 %, TIER 0 excluded, with recorded exceptions), and SHALL NOT activate them in this spec, so that the current suite keeps passing until spec 005b has applied the cleanup.
- FR-9: THE SYSTEM SHALL produce an audit report of the existing tests that assigns one verdict to every test group, identified by an id, with the reason, the behavior it protects, and, for DELETE and REPLACE, the test or strategy that keeps the protection. The report SHALL be structured so that the user can approve it group by group, and SHALL change no existing test while it is produced. The user's choice per group is given as the answer at the approval gate of the 005b spec, whose spec lists the approved group ids; the report file itself is not an approval. WHEN 005b starts, THE SYSTEM SHALL re-check the report against the current tests, taking as reference the test files and their content at the commit that closes 005a, and mark REVIEW every group that changed since then. In 005a this re-check is satisfied by the rule being written in the skill and the flow rules; it is executed when 005b starts.
- FR-10: THE SYSTEM SHALL classify as CORE the components that the protected tests protect (owner isolation and, when it exists, spoiler filtering), SHALL list the protected tests individually inside their group in the audit report as untouchable (the owner-isolation tests now; the spoiler tests as soon as they are created, in Phase 4), SHALL NOT classify the tests themselves, and SHALL give them only the verdicts KEEP or REVIEW, individually. A verdict given to the group never applies to the protected tests inside it, and approving a group in 005b does not cover them. Any change to a protected test needs its own explicit approval of the user at a flow gate and SHALL NOT reduce what it checks. The only case where a protected test may be proposed for deletion is when the production behavior it protects is removed entirely (D-6): the proposal goes test by test, needs the explicit approval of the user at a flow gate, and SHALL show that no other remaining path loses its protection.
- FR-11: THE SYSTEM SHALL provide a written recommendation, based on the analysis of the project, for the distribution between unit, integration and end-to-end tests, starting from a diagnosis with numbers (volume of production code against volume of test code, and the current split of tests by type), and a written evaluation (benefit, cost and complexity, without installing anything) of mutation testing, extra static analysis, scripts that detect redundant tests and mechanisms to keep the inventory up to date.
- FR-12: THE SYSTEM SHALL provide an operational skill named `quality-testing-core`, referenced from a light addition to the project instructions, that lets an agent: classify a component, know the expected coverage, choose what behaviors to protect and the test type, tell a useful test from a coverage-only test, find out whether a behavior is already covered, decide whether a test can be simplified or removed, manage the inventory, tell coverage from real quality, apply the strategy of each test type, decide when a mock or fake is acceptable and when it hides real errors, and know which of the project's verification checks to run before finishing. The skill SHALL also state the rules of FR-13, FR-14 and FR-15, including the rule for tooling. Creating the skill folder needs the user's approval in the plan, because the project structure is owned by the user.
- FR-13: WHEN a task changes the behavior of a CORE or IMPORTANT component, THE SYSTEM SHALL require its tests to be written first and seen failing for the expected reason (red step) and then the code written until they pass (green). WHEN a task keeps behavior (refactor, rename, move, removal of code without behavior change), THE SYSTEM SHALL require no new test and SHALL require the existing tests that protect the behavior to pass before and after; the only exception is a CORE or IMPORTANT component whose behavior is not yet protected (a known gap), for which characterization tests that pin the current behavior are written first, pass on the current code, and the change is then made with green before and after (the only case where a behavior-keeping change adds tests). WHEN a task removes a behavior of a CORE or IMPORTANT component, THE SYSTEM SHALL precede the change with a proposal to delete the tests of that behavior, subject to the approval of the user (FR-15); when some of those tests are protected tests, the proposal goes test by test and shows that no other remaining path loses its protection (D-6, FR-10). In every case THE SYSTEM SHALL record under the task in the task list one line that says which happened (red then green; green before and after; characterization then green before and after; or behavior removed with the approval) and names the tests involved, so that validation can check it.
- FR-14: THE SYSTEM SHALL write no tests for TIER 0 components, bug fixes included: a bug in a TIER 0 component is fixed without a test, unless FR-2 reclassifies the component. WHEN a bug is fixed in a CORE or IMPORTANT component, THE SYSTEM SHALL require first a test that reproduces it and fails. Tooling (test support and custom lint rules) is not classified: a change to it carries tests only when it changes a check that protects a CORE or IMPORTANT component (for example an import-boundary lint rule).
- FR-15: From the closing of spec 005b on, THE SYSTEM SHALL let the skill propose deleting or simplifying a test case by case (including the tests of a removed behavior, FR-13), with a written justification that no protection is lost, and SHALL delete or simplify nothing without the explicit approval of the user at a flow gate; protected tests SHALL never be proposed for deletion, except when the production behavior they protect is removed entirely (D-6), in which case the proposal goes test by test, needs the user's explicit approval at a flow gate and SHALL show that no other remaining path loses its protection.
- FR-16: THE SYSTEM SHALL change the project instructions and the flow rules only in the following list of categories, as approved by the user on 2026-11-20, and nothing outside it: (a) the rule "tests with every change" becomes "tests proportional to criticality" (CORE and IMPORTANT changes carry tests, TIER 0 changes carry none) in every place of the project instructions, the flow rules, the commands and the agent definitions that restates "tests with every change" or "none deleted", or that copies the plan or task template; plus, explicitly, the architecture rule's table of test type per layer and its tests tree (aligned with the recommended distribution of FR-11 and the unit-level component tests of FR-7), and the Commands section of the project instructions if a coverage command is added; (b) the NEVER rule about silencing errors, skipping and deleting tests and relaxing strict mode gains the exception "except a justified proposal approved by the user" for deleting or simplifying tests only, and the other three stay forbidden without exception; (c) the plan and task templates gain the test design section and the evidence line (FR-13, FR-17); (d) validation gains the checks of FR-18; (e) the numbering, folder and branch rules (FR-19); (f) the "Current status", the roadmap, OD-6 and the references to spec 005 in the data-model rule (FR-20); (g) the Structure section lists the new skill (FR-12); (h) the Stack section records the tool approvals, if granted (FR-7).
- FR-17: WHEN a plan or a task list is written, THE SYSTEM SHALL include in each a test design section that states, for every affected component, its criticality, the behaviors to protect and the test type chosen. WHERE the spec has no production component with behavior (documentation, process or tooling, as this spec, whose only production change is the TIER 0 entry of the development dependencies in the package manifest and its lockfile), the section SHALL say "no production component with behavior" and FR-13 and FR-18 do not apply.
- FR-18: WHEN a spec is validated, THE SYSTEM SHALL check that every affected component is classified, that each CORE or IMPORTANT task shows the line required by FR-13 and, where it says red then green or characterization, that the tests named exist, where it says behavior removed, that the approval is recorded, and that no tests were added for TIER 0 components.
- FR-19: THE SYSTEM SHALL adopt, from this spec on, the convention that specs born from one shared context are numbered with the same number and consecutive letters (NNNa, NNNb, ...), with branch names made of the prefix `spec-`, the number with its letter and the feature name, and the flow rules that define spec numbering, spec folder names and branch names SHALL be updated to say so.
- FR-20: THE SYSTEM SHALL update the roadmap (the list of specs and the description of Phase 1, which today counts four specs, the note that the numbers are provisional and the "needs resolved first" column of Phase 1), the "Current status" of the project instructions, the text of OD-6 in the open decisions, and the references to spec 005 as the lifecycle spec in the data-model rule, so that the quality work appears as specs 005a and 005b, placed inside Phase 1 and before spec 006, and the universe lifecycle, including the trash decision of OD-6, appears as spec 006.

## Non-functional requirements

- NFR-1: This spec SHALL NOT change production behavior, add tests of production code, or delete, skip or alter any existing test; after its tasks, the project's verification checks and the full suite (unit, integration and browser tests) give the same result as before, meaning the same tests exist and each has the same pass or fail outcome. Installing the coverage provider and the test environment is allowed provided no existing test changes its outcome.
- NFR-2: The new lines added to the project instructions for the reference to the skill SHALL NOT exceed 15; lines rewritten under the closed list of FR-16 do not count toward that limit, and no existing instruction outside that list SHALL change.
- NFR-3: Every production file SHALL map to exactly one inventory entry, checked by listing the production files and matching each against the inventory; an unmatched or duplicated file is a defect.
- NFR-4: The audit report SHALL cover 100 % of the existing test files, each in exactly one test group with one verdict, checked by listing the test files and matching each against the report.

## Spoiler impact

None. This spec concerns tooling and the way of working; it reads and writes no narrative information and no information with a spoiler boundary. The only relation is protective: the owner-isolation tests exist today and are protected (FR-10); the spoiler filtering suite does not exist yet (Phase 4) and its tests become protected, and their components CORE, as soon as they are created.

## Edge cases

- A component mixes behavior and declaration (for example a configuration object with a computation): it is classified by its riskiest behavior, or split in the inventory.
- A CORE target of 100 % needs a branch that cannot be reached (defensive code): the exception is recorded in the inventory entry with its reason; it is not covered with an artificial test.
- A component has no tests today and is CORE or IMPORTANT: the audit report lists the gap as a finding, and the work to fill it belongs to 005b or to a later spec.
- A group of tests cannot be judged with the information available: it gets REVIEW with the missing information named, and 005b does not touch it unless the user decides.
- A behavior is protected only by a browser test: coverage figures do not show it, so the inventory records "protected by browser test X" and the report does not count it as a gap.
- A protected test lives in a file with other tests: protection applies to that test only; the report lists it individually inside its group.
- A test protects a component that is later deleted from production: the audit and the skill treat it as a candidate for DELETE with that reason, and under FR-15 the deletion still needs the user's approval. If the test is a protected test, D-6 applies: it is proposed only because the behavior is removed entirely, test by test, with the user's explicit approval and showing that no other remaining path loses its protection.
- A component is renamed, moved, merged or deleted: its inventory entry is updated in the same task.
- A bug is found in a TIER 0 element: it is fixed without a test; if the fix reveals relevant logic, FR-2 applies.
- A change touches only a TIER 0 element but breaks a type check: the type checker is the protection; no test is added.
- A spec has no production component with behavior: the test design section says so, and no red step or green-before-and-after line is expected.
- A protected test is still in use by remaining behavior, or the behavior it protects is only partly removed: it is not proposed for deletion (D-6 requires the behavior to be removed entirely).
- A behavior-keeping change touches a CORE or IMPORTANT component whose behavior has no protecting test: characterization tests are written first and pass on the current code, then the change is made with green before and after.
- A task removes a behavior of a CORE or IMPORTANT component: a proposal to delete the tests of that behavior comes first; the evidence line says "behavior removed" and records the approval.
- A change touches only tooling (test support or a custom lint rule): no test is added, unless the change alters a check that protects a CORE or IMPORTANT component, such as an import-boundary lint rule.
- A protected test sits inside a group that the user approves in 005b: the group approval does not cover it; it keeps KEEP or REVIEW and changes only with its own explicit approval.

## Out of scope

- Deleting, refactoring or replacing any existing test, writing component tests and any other new test of production code, and filling coverage gaps: spec 005b (or the task that next touches the component, FR-13). The bulk cleanup approved group by group is the only exception to the "never delete tests" rule; after it, every deletion or simplification needs the user's approval case by case (FR-15), and protected tests are never changed without their own explicit approval (FR-10); a protected test is proposed for deletion only when the behavior it protects is removed entirely (D-6).
- Activating the automatic coverage thresholds: spec 005b.
- Installing mutation testing, extra static analysis or redundancy-detection scripts: they are only evaluated in writing.
- Changing any instruction or flow rule outside the categories listed in FR-16.
- New commands or new agents for the flow.
- Changes to production code, to the data model or to any narrative feature. The only exception is the development dependencies in the package manifest and its lockfile when the tools of FR-7 are approved (TIER 0 entry).
- Known leftover: two code comments still call "spec 005" the universe lifecycle spec (one in the database schema, one in the universe repository interface). They are left as they are in 005a (production code is out of scope and schema changes need approval) and are to be corrected by spec 006 when it touches those files.
- Items in `docs/roadmap.md` out-of-scope list and the open decisions in `docs/open-decisions.md` (none of them is touched by this spec except the renumbering text of OD-6 in FR-20; OD-22, Prettier and GitHub Actions, stays open, so no CI step is added for coverage).

## Completion criteria

- Every FR above is verifiable by the reviewer against the documents produced.
- An agent that reads only the skill and the inventory answers the eight questions of the precedent document for a fixed set of at least 8 real components of the project, chosen by the user or listed in the plan, covering the three levels: (1) what criticality the component being modified has; (2) what coverage is expected from it; (3) which behaviors deserve protection; (4) which test type fits best; (5) whether a test being written is useful or only raises coverage; (6) whether a test already covers the behavior; (7) whether a test can be simplified or removed without losing guarantees; (8) which checks to run before considering the work done. The answers must match the inventory entry of each component, and "consistently" means that two independent runs give the same level and the same test type. The final judgment may be a manual check by the user.
- The audit report exists, covers every test file (NFR-4) and is ready to be approved group by group.
- Manual check by the user: the roadmap and the current status read correctly after the renumbering, and the precedent document `CALIDAD.md` is removed only when the user confirms that its content is covered (it is kept until then).
