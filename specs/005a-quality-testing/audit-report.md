# Audit report 005a — Existing tests

This is a point-in-time document, not an approval. Approval is the user's answer at the approval gate of spec 005b, which lists the approved group ids. Producing this report changes no test (FR-9, NFR-1).

## How to read it

- Every test file under `tests/` belongs to exactly one **test group** (one file, or a set of files that protect the same component). Each group has a stable id (`A-01`, ...) that the user cites at the 005b gate, and **exactly one verdict** (FR-9, NFR-4).
- Each test file is listed with the first 12 characters of its git blob id (`git hash-object <file>`) at the time the report was written.
- The reason of every verdict cites the eleven audit criteria below by number (C1 to C11). Assertion quality is judged with `.claude/skills/quality-testing-core/references/assertion-quality.md`; the expected test type with `testing-evaluation.md` section 2 and `references/test-type-strategies.md`; the components with the inventory entry ids of `docs/criticality-inventory.md`.
- Overlap with a lower level is a reason to examine, not a verdict by itself. Line numbers refer to the file at the blob id listed.
- The procedure is `.claude/skills/quality-testing-core/references/audit-and-removal.md`.

## The eleven audit criteria

| Id | Criterion (`CALIDAD.md` section 6) |
|---|---|
| C1 | Redundant tests that check the same behavior |
| C2 | Generic tests that check no relevant result |
| C3 | Weak or insufficient assertions |
| C4 | Tests that check implementation details |
| C5 | Tests too coupled to internal code |
| C6 | Tests that use mocks unnecessarily |
| C7 | Tests that hide real errors behind mocks |
| C8 | Tests that do not justify their maintenance cost |
| C9 | Tests of TIER 0 components that add no value |
| C10 | CORE or IMPORTANT components without enough protection |
| C11 | Integration or end-to-end tests that duplicate other levels unnecessarily |

## Verdicts

| Verdict | Meaning | Column it requires |
|---|---|---|
| `KEEP` | Gives real protection | `Behavior protected` |
| `REFACTOR` | Valid intention, deficient implementation | `Reason`: what to change, with line numbers |
| `DELETE` | Redundant, artificial or without value | `Protection kept`: the test or strategy that keeps the protection |
| `REPLACE` | A better strategy exists to protect the behavior | `Protection kept`: the replacement and why it protects at least as much |
| `REVIEW` | Information is missing to decide | `Missing information` |

## Protected tests are never covered by a group verdict

**A group verdict never applies to the protected tests inside it, and approving the group in 005b does not cover them.** Protected tests (owner isolation now; spoiler filtering from Phase 4) are listed individually in section C and get only `KEEP` or `REVIEW`, individually. Any change to a protected test needs its own explicit approval of the user at a flow gate and never reduces what it checks (FR-10, D-6).

## The 005b re-check by blob ids

The report stores, for each test file, the **first 12 characters of its git blob id** at the time the report is closed (`git hash-object <file>`). When 005b starts:
1. Recompute the ids at the commit that closes 005a. It equals the commit where the report was written, because 005a changes no test (NFR-1).
2. Compare them with the current ids: one `git hash-object <file>` per file listed. No script is needed.
3. Mark `REVIEW` every group with at least one different id, an added file or a removed file, **before** the user is asked.

The protected tests of a group marked `REVIEW` this way are re-checked individually as well.
