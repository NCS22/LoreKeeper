# Spec 005b — Test cleanup and coverage thresholds

Status: approved

## Context and goal

Spec 005a (implemented 2026-11-24) defined the testing strategy and produced the knowledge this spec needs, without changing any test: a criticality inventory with a coverage target per entry, a report that measures coverage per entry, an audit report with one verdict per group of existing tests (105 groups) and a list of protected tests (29). Its two last promises were left for this spec: the verdicts the user approves are applied, and the automatic coverage thresholds that 005a only defined are turned on.

This is the second of the two specs that share one context (the user's source document of 2026-11-20, kept until both are done). It is the only moment where tests are deleted or rewritten in bulk, and only the groups the user approves one by one. After it closes, every deletion or simplification of a test is a case-by-case proposal (005a FR-15).

The goal is not a smaller suite: the audit says the reduction must be a consequence of removing unnecessary work, never a number to reach. The goal is that, when this spec closes, the suite protects what the audit says it protects with less weakness and less redundancy, every gap of a CORE or IMPORTANT component is either closed or explained, and the coverage targets stop being only a report and start failing when a component falls below them.

- D-2. **A-26 (REVIEW).** The group keeps only the check, made at the type level, that the error log cannot accept passwords or request bodies, and the rest of the group is removed, because the logging behavior is protected through the error mapper and the action runner (A-29, A-32). It follows the precedent of the design tokens entry, which is TIER 0 and keeps its existing contrast test by a recorded decision; the exception is recorded in the inventory entry of the component (FR-12).
- D-3. **Protected tests marked REVIEW.** P-06 is kept as it is (KEEP): the outcome it relates to is proven through real calls by P-17, P-18 and P-28. P-16 is strengthened with a control insert that proves the database would accept a valid write, and with an assertion of the specific error, without checking less than before. This answer is the individual explicit approval that the protected tests require for these two tests; it covers no other protected test.
- D-4. **Coverage gaps (hybrid).** ACC-2 and UNI-4 get an override and not new tests (D-8, which replaces the first version of this decision). SHR-1 gets an override with its reason. The IMPORTANT interface entries get a "floor" that equals their current measured figure, so that they cannot go down, with the plan "raise it when the component is next touched". Small tests are written only where they protect a behavior and bring the entry to its target (for example CMP-7, APP-3 and CMP-10, as the plan decides). Full component tests for the IMPORTANT screens go to a later spec and are not part of this one; no split into another spec is needed.
- D-5. **Thresholds.** Only the coverage command fails; the ordinary test command does not change. The coverage command also fails when a production file has no inventory entry or has two. The coverage command becomes a required check at the validation of each spec, not at each task. This spec's cleanup additionally measures the coverage of the affected entries after each group (FR-6) because it is the one spec that removes tests in bulk.
- D-6. **Constitution edit.** The user approved, with the answer of D-5, the edits to the project instructions and to the flow rules listed in FR-12, and nothing outside that list. They are part of this spec and land with it, as in 005a, and are not a separate documentation change.
- D-7. **Raising a floor.** WHEN an entry's measured figure is above its floor (or, by extension, above its override), the coverage command prints a notice and does not fail. The validation of every spec requires that no such notice remains, whatever the cause of the rise: the floor or override is raised to the new measured figure, or removed when the entry reaches its target (FR-10, FR-12).
- D-8. **ACC-2 and UNI-4.** No new tests for these two entries; each gets an override with its real measured figures and the reason below, and production code is not touched (NFR-1). Reason for UNI-4: the system can never hold a stored universe mode other than the two it knows, so the refusal of an unknown mode cannot happen today, and covering it would need an invented stored value that the system itself does not allow, an artificial test. Reason for ACC-2: a return destination whose whole address can be decoded always has a decodable path, so the separate refusal of an undecodable path can never be reached, and covering it would need an artificial input. This replaces the "new behavior tests" part of D-4. SHR-1 stays as written in FR-7.

### Decisions inherited from 005a

- D-3 and D-6 of 005a stand. Nothing is deleted or simplified without the user's explicit approval at a flow gate. A protected test is proposed for deletion only when the production behavior it protects is removed entirely, test by test, showing that no other remaining path loses its protection. This spec removes no production behavior, so it deletes no protected test.
- The coverage policy of 005a stands: CORE 100 %, IMPORTANT 80 %, TIER 0 excluded, lines and branches, per inventory entry, with an exception recorded in the entry when a target cannot be reached without redundant, fragile or low-value tests. This spec does not change those values; it adds one kind of recorded exception, the floor (FR-8), for an IMPORTANT entry whose target is postponed and not unreachable; a CORE entry never records a floor (D-I5 of the decision record).

## Users

- The project owner, who approved the groups, the protected-test decisions, the gap handling and the check at validation, and who confirms the final state.
- The AI agents (planner, implementer, reviewer, coordinator), who must find the thresholds working and the inventory truthful.

## User stories

- US-1. As the project owner, I want the cleanup applied group by group, each one checked against the audit, so that nothing is changed on an outdated judgment and the suite is green after each step.
- US-2. As the project owner, I want protected tests to stay untouched unless I approve each one individually, so that the guarantee that one account cannot reach another's data never weakens by accident.
- US-3. As the project owner, I want every coverage gap closed with a real test or recorded with a reason, so that no CORE or IMPORTANT component is silently below its target or can go lower.
- US-4. As the project owner, I want the coverage targets to fail loudly when a component falls below them or a file has no entry, so that the percentage is a safety net and not a report nobody reads.
- US-5. As an AI agent, I want the inventory, the skill and the checks to agree after the cleanup, so that I do not follow a rule that says the thresholds are not active or that a gap fails nothing.

## Definitions

- **Audit report**: the report of spec 005a, a frozen snapshot of the state that closed 005a. It is not edited by this spec.
- **Approved group**: a test group whose id is in D-1.
- **Re-check**: comparing the content of each file of a group with the content recorded for it in the audit report. The record is per file, so a protected test is re-checked by re-reading it against what the report says it proves.
- **Override**: the exception of the coverage policy for a target that cannot be reached without redundant, fragile or low-value tests; recorded in the inventory entry, per metric, with its reason.
- **Floor**: a recorded exception, allowed only on an IMPORTANT entry, for a target that is not reached yet because its tests are postponed. It holds the entry at its measured figure, per metric that is below its target, with the plan to raise it. It replaces the former "gap" record.
- **Combined coverage**: lines and branches of an entry counted over the unit, integration and component tests together; browser tests are not measured.
- **Not measured entry**: an entry none of whose files is in the measured source (configuration outside it, or files that are not code); the inventory names the tests that protect it.
- **Validation of a spec**: the phase of the flow that runs when every task is done, before closing.

## Functional requirements

- FR-1: WHEN an approved group is about to be applied, THE SYSTEM SHALL compare every file of the group with the content recorded for it in the audit report; IF any file differs, was added or was removed, THEN THE SYSTEM SHALL NOT apply the group, SHALL record in the decision record of this spec that the group is back to REVIEW (the audit report is frozen and is not edited), SHALL re-read the protected tests inside the changed files against what the report says each proves, and SHALL ask the user.
- FR-2: THE SYSTEM SHALL remove or rewrite existing test cases only in the 18 approved groups, one group at a time, each in its own unit of work with the ordinary test command passing after it, in an order where a group that holds the protection another group names is applied before the group that relies on it; WHERE groups name each other or the report names no protection, the plan fixes one order and states it, and FR-6(b) guarantees that no behavior loses its last copy whatever the order. The only other changes to tests are those the decisions authorize: the strengthening of the existing case P-16 (D-3), which changes that case and nothing else, and the tests added to close gaps (FR-7 for a reachable SHR-1 path, FR-8 for the small tests of IMPORTANT entries), which add cases or files, also in the files of groups of any verdict; neither removes or weakens any other existing case of a group that is not approved. The outcome of each group (applied or skipped, and why) SHALL be recorded in the task list of this spec, and a skip or a return to REVIEW also in its decision record; the spec itself does not receive results.
- FR-3: THE SYSTEM SHALL NOT change, move, weaken or delete any protected test through the approval of a group, whether the test lives in the group or runs through it. P-16 is the only protected test changed (D-3) and SHALL check at least what it checked before; P-06 stays as it is. Any other change to a protected test needs its own explicit approval of the user that names the test. IF the change to an approved group would alter a protected test, THEN THE SYSTEM SHALL change the rest of the group only, or stop and ask.
- FR-4: WHEN the approved group A-17 (DELETE) is applied, THE SYSTEM SHALL delete only its tests, after showing that the protection the report names as kept exists and passes. WHEN an approved REFACTOR group is applied, THE SYSTEM SHALL change its tests as the report's reason describes, leaving production behavior unchanged and using no new tool or configuration. WHERE the reason offers alternatives, THE SYSTEM SHALL choose by one criterion, stated for each group in the plan for the user's approval: the alternative that keeps every behavior the report lists as protected by the group checked by a test; an assertion that can be made exact is made exact rather than removed; a test is removed only when the report names another test that checks the same behavior and the plan shows that it does; a check of speed that depends on the wall clock is replaced by a measure of work, or, when the code exposes none, removed with the plan stating that speed is not protected.
- FR-5: WHEN group A-26 is applied, THE SYSTEM SHALL leave in it the check that fails the type check if the error-log context can accept a password or a request body, and SHALL remove the other cases of the group after showing that the error mapper and action runner tests (A-29, A-32) still check the logging behavior. Whether the trivial runtime assertion of the kept case stays is decided by the plan, provided the type check itself stays.
- FR-6: WHEN a group is applied, THE SYSTEM SHALL check that (a) the ordinary test command passes and every protected test that runs in it passes; (b) every behavior the report lists as protected by the group is still checked by at least one remaining test, so that no behavior loses its last copy even when several groups trim copies of the same rule; (c) the combined coverage of every CORE and IMPORTANT entry the group protects is not lower than before (TIER 0 entries are not part of this check); and (d) for a group of browser tests, which coverage does not measure, the browser tests and protected browser tests that the group's kept protection relies on pass. IF any of them fails, THEN the group SHALL be stopped and go back to REVIEW.
- FR-7: THE SYSTEM SHALL close the gaps of the CORE entries as follows: ACC-2 and UNI-4 each with an override recorded in its entry, with the figures measured after the groups are applied and the reason of D-8, and without any new test or any change to production code; SHR-1 with an override recorded after all groups are applied, with the figures measured at that time, whose reason names each path that stays uncovered and why a test of it would be artificial (for example, that it only runs in the server during browser tests); a path of SHR-1 that a test of behavior can reach is tested instead. A test added SHALL protect a behavior and be of the type the skill chooses; a test written only to execute a line is not allowed.
- FR-8: THE SYSTEM SHALL close the gaps of the twelve IMPORTANT entries (APP-3, APP-4, APP-5, APP-6, CMP-2, CMP-4, CMP-5, CMP-7, CMP-8, CMP-9, CMP-10, CMP-11), after the groups and the CORE tests are applied, in one of two ways per entry: small tests of behavior, named in the plan with the figure expected, that bring the entry to 80 % in both metrics (no partial tests: an entry that would stay below 80 % gets none); or a floor. A floor is written, in the exact form the inventory defines, with the measured figure of each metric that is below its target, as printed by the coverage report (one decimal); a metric already at or above its target keeps the policy target, and a metric with nothing to measure (no branches) is left out. The floor carries the plan "raise it when the component is next touched"; the notice and the validation rule that enforce it are in FR-10 and FR-12 (D-7).
- FR-9: WHEN a group is applied or a gap is closed, THE SYSTEM SHALL update the entries it touches in the criticality inventory (protection snapshot, exceptions and floors) and SHALL keep every production file in exactly one entry. From this spec on, a CORE entry below its target carries an override, and an IMPORTANT entry below its target carries an override or a floor; a CORE entry never carries a floor; the "gap" record is no longer written, and a component reclassified upward that is below its new target gets tests or an override in the same task (also a floor if the new level is IMPORTANT).
- FR-10: THE SYSTEM SHALL turn on the coverage thresholds of 005a: WHEN the coverage command runs, IF a CORE entry has lines or branches below 100 %, or an IMPORTANT entry below 80 %, in the combined coverage, with overrides and floors applied (an override or a floor replaces the target of its metric) and TIER 0 excluded, THEN THE SYSTEM SHALL end with a failure and print, for each failing entry, its id, the metric, the measured figure and the target. A metric with nothing to measure is not applicable and does not fail. A not measured entry is printed as not measured and does not fail. The comparison with a floor, an override or a target is made on the figures as printed, with one decimal, so that a figure written as printed does not fail at once and a drop of at least the printed precision does; a drop smaller than that precision is not detected. WHEN the printed figure of a metric of an entry is above its floor or its override, THE SYSTEM SHALL print a notice naming the entry, the metric, the figure and the floor or override, without failing (D-7). IF an override or a floor is not in its written form or has no reason or plan, or a floor is recorded on a CORE entry, THEN THE SYSTEM SHALL fail, SHALL NOT apply that floor, and SHALL name the entry. The ordinary test command SHALL NOT fail because of coverage and SHALL behave as before.
- FR-11: IF the coverage command finds a production file that matches no inventory entry, or matches two, THEN THE SYSTEM SHALL end with a failure and name the file. The existing warning for an inventory pattern that matches no file stays a warning. WHEN the cleanup and the gap closure are finished, THE SYSTEM SHALL pass the coverage command on the repository.
- FR-12: THE SYSTEM SHALL make the coverage command a required check at the validation of every spec, and not at each task, and SHALL change the project instructions, the flow rules, the commands and agent definitions that copy them, the skill and the inventory only in the following closed list, approved by the user on 2026-11-24 (D-6): (a) the verification list of the project instructions keeps its per-task checks and gains a separate line that the coverage command passes at the validation of a spec, and the validation section of the flow rules (with the commands and agent definitions that restate the validation checks) says the same, and adds that the validation requires that no floor or override notice remains, whatever the cause of the rise: each is raised to the new measured figure or removed when the entry reaches its target (D-7); (b) the commands section of the project instructions describes the coverage command as failing below the targets and on an unmatched or duplicated production file; (c) the "Current status" of the project instructions and the roadmap, where they say the thresholds are not active or the cleanup is pending, are updated when the spec closes; (d) in the skill and the inventory, every statement that the thresholds are not active, that a gap or a reclassification below target "fails nothing", and the definitions of exception and gap, are rewritten for overrides, floors and the thresholds being active (this includes the part of the inventory that explains how to read it); (e) the inventory entry of the error-log component records the retained check of D-2 in its strategy; (f) the inventory entry that lists the user's source document as a non-production file stops listing it once the user has confirmed its removal (completion criteria).

## Non-functional requirements

- NFR-1: This spec SHALL NOT change production behavior, the data model or any narrative feature. Only tests, test support, the coverage tooling and documents change.
- NFR-2: At least the 29 protected tests of the audit report SHALL exist and pass before and after the cleanup; P-16 changes only as D-3 allows.
- NFR-3: No target number of tests, test lines or runtime is set for the cleanup. Each deleted or rewritten group has the reason of the audit report; the size of the reduction is reported, not required.
- NFR-4: After the cleanup every test file belongs to exactly one group: the audit report's group of the component it tests, or a new group that the plan names for a test file this spec adds; a case added to an existing file stays in that file's group.

## Spoiler impact

None. This spec concerns tests and coverage tooling; it reads and writes no narrative information. The relation is protective: the owner-isolation tests (the protected tests) must exist and pass before and after the cleanup (FR-3, NFR-2). The spoiler-filtering suite does not exist yet (Phase 4) and is not touched.

## Edge cases

- A test file changed after the audit report was written: its group is not applied until the user decides (FR-1). On 2026-11-24 none had changed.
- A group is approved but its change would need a production change: the group is not applied and the user is told; production behavior is out of scope (NFR-1).
- A group approved as DELETE or REFACTOR names a protection that lives in another approved group (the authenticator group for the session-policy and the Better Auth groups; the three browser groups that each trim their own copy of the same rule): the group that keeps the protection is applied first; where groups name each other, the plan fixes one order; in every case the protection is checked after each group and the last copy of a behavior is never removed (FR-2, FR-6).
- An approved group contains a protected test, or runs one that is listed in another group: the rest of the group is changed and the protected test is left as it is (FR-3).
- Removing or rewriting tests lowers the coverage of a CORE or IMPORTANT entry, or leaves a listed behavior with no test: FR-6 stops the group and it goes back to REVIEW; the report's protection kept was insufficient.
- Removing tests lowers the coverage of a TIER 0 entry (for example the error-log entry after A-26): it is not checked and is not a failure.
- A CORE target of 100 % needs an unreachable branch (defensive code): the entry records an override with its reason; it is not covered with an artificial test.
- An IMPORTANT entry is below its target only because browser tests, which are not measured, protect it: it gets a floor, not a bare gap record, because the thresholds would fail (FR-8).
- A CORE entry is below 100 % and its tests are postponed: it still records no floor; it reaches 100 % or records an override with its reason, and a floor written on it makes the coverage command fail (FR-9, FR-10).
- A floor is recorded and a later change lowers the measured figure of that entry: the coverage command fails; the fix is a test, never lowering the floor.
- A change, direct or indirect, raises the measured figure of an entry above its floor or override (for example through a test of another component): the coverage command prints a notice and the validation of that spec requires the floor or override to be raised or removed; no judgment about what the spec "touched" is needed (FR-10, FR-12, D-7).
- An entry has no branches (a wiring file) or its figure is above 80 % in one metric (a provider with a tested reducer): the metric without items is skipped, the other metric keeps its own rule (FR-8, FR-10).
- A CORE entry is not measured because its files are outside the measured source (the framework configuration, the database schema): it is printed as not measured, never silently skipped from the output, and the tests that protect it stay named in its entry.
- A figure is exactly at the target and a later change drops it by at least the printed precision (one decimal): the command fails; a drop smaller than that precision is not detected (FR-10).
- A new production component appears without an inventory entry: the coverage command fails and names the file (FR-11); the inventory rule that the task that adds it writes its entry stays, and the check at validation catches a task that forgot.
- The coverage command cannot run because the local database is not started: it fails loudly, as the ordinary test command does, and no threshold result is reported.
- The audit report stays unchanged; its figures are a snapshot. The outcome of this spec is recorded in its task list, its decision record and the inventory.

## Out of scope

- Production code, the data model and narrative features (NFR-1).
- Changing the policy values (CORE 100 %, IMPORTANT 80 %, TIER 0 excluded) or the metrics (lines and branches).
- Deleting protected tests, and changing any protected test other than P-16 (FR-3); no production behavior is removed here, so D-6 of 005a does not apply.
- Full component tests for the IMPORTANT interface components (screens, forms, menus, layout): they go to a later spec, and their floors stay until then (D-4). Only small tests that bring an entry to its target are written here (FR-8).
- New tools or configuration to move or run a test somewhere else (for example a separate performance suite): FR-4 uses none.
- Running the coverage command at each task (D-5), and any change to the ordinary test command.
- Mutation testing, extra static analysis of tests and scripts that detect redundant tests: 005a evaluated them; the recommended one-off mutation run after this cleanup needs approval of a new development dependency and is a separate decision.
- Continuous integration and Prettier (OD-22 stays open): the thresholds are checked by the command a person or an agent runs; no pipeline step is added.
- Editing the audit report (a frozen snapshot), the testing evaluation, or the skill and inventory text beyond the closed list of FR-12.
- The universe lifecycle (spec 006) and the two comments that still call it "spec 005" (left for 006).
- Items in the out-of-scope list of `docs/roadmap.md` and the open decisions of `docs/open-decisions.md` (none is touched).

The same temporary checks show that it prints a notice, without failing, when an entry's figure is above its floor or its override. The ordinary test command is unchanged.
- ACC-2, UNI-4 and SHR-1 each carry an override with the figures measured after the groups are applied and its reason, and no test was added for ACC-2 or UNI-4; every IMPORTANT entry below target carries a floor or reaches 80 % through its named small tests, each recorded in its entry with the figures.

- Manual check by the user: the roadmap and the current status read correctly, and the user's source document of 2026-11-20 is removed only when the user confirms that both 005a and 005b cover its content (it stays until then; the removal is a closing step done after that confirmation, and the inventory entry of FR-12(f) is updated with it).
